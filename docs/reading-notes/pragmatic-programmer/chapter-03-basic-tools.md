## Core themes to review

Chapter 3 focuses on the tools that support everyday software development.

The main areas to reflect on are:

- using plain text as a flexible and long-lasting format;
- becoming comfortable with the command line;
- improving speed and accuracy in the editor;
- using version control consistently;
- debugging with discipline instead of guessing;
- using text manipulation tools to inspect and transform information;
- keeping notes that capture useful decisions, discoveries, and lessons.

## Three important ideas

### 1. Tools shape how I think and work

A developer’s tools are not just accessories.

The editor, terminal, version control system, debugger, note-taking system, and
automation scripts all affect how quickly and clearly I can solve problems.

Reflection prompt:

- Which tool do I currently use only at a basic level, even though improving at
  it would make my daily work noticeably better?

### 2. Plain text makes knowledge easier to inspect and move

Plain text is simple, searchable, versionable, and easy to reuse.

When important project knowledge is stored in clear text formats such as
Markdown, configuration files, scripts, or structured notes, it becomes easier
to track changes and share understanding.

Reflection prompt:

- Which useful project knowledge is currently trapped in screenshots, chats,
  memory, or scattered documents instead of being stored in a clear text file?

### 3. Debugging should be deliberate

Debugging should not be random trial and error.

A pragmatic debugging process starts by reproducing the problem, observing the
facts, forming a clear hypothesis, testing that hypothesis, and recording what
was learned.

Reflection prompt:

- In my recent debugging work, did I gather enough evidence before changing the
  code, or did I start guessing too quickly?

## Two possible applications

### 1. Improve one everyday tool this week

Choose one tool and deliberately practise it.

Possible options:

- learn five useful editor shortcuts;
- create or improve a terminal command workflow;
- improve Git branch and pull request habits;
- practise reading diffs before committing;
- create a reusable Markdown note template;
- learn one useful text-search or text-processing command.

Action:

- choose one tool;
- define one small improvement;
- practise it during real project work;
- record what changed in speed, confidence, or quality.

### 2. Create a debugging checklist

Create a short checklist to use before changing code during a bug investigation.

The checklist should include:

- Can I reproduce the problem?
- What changed recently?
- What evidence do the logs, error messages, or tests show?
- What is my current hypothesis?
- What is the smallest test that can confirm or reject that hypothesis?
- What did I learn after testing?

## Remaining question

How do I decide which tools are worth learning deeply versus which tools are
only worth knowing at a basic level?

## Working answer

A tool is worth learning deeply when it appears often in my work, reduces
repeated effort, improves accuracy, helps me debug faster, or makes collaboration
clearer.

A tool may only need basic knowledge when it is rarely used, easily replaced, or
not central to the type of work I am trying to improve.

The goal is not to collect tools. The goal is to build a reliable working
environment that helps me think, test, communicate, and deliver better software.

## Personal takeaway

Basic tools are not basic because they are unimportant.

They are basic because they are used constantly. Small improvements in daily
tools can compound into better speed, fewer mistakes, and clearer thinking.
